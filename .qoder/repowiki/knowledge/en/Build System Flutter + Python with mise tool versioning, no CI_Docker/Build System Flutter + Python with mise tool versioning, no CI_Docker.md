## What system/approach is used

This repository has no centralized build orchestration (no `Makefile`, no `Dockerfile`, no `.github/workflows`, no CI pipeline). Build and dependency management are delegated to the native tools of each subproject:

- **Flutter app** (`whoosh_ramah/`): built via the Flutter SDK using `flutter pub get`, `flutter build apk|ios|web`, etc. Dependencies are declared in `pubspec.yaml`.
- **Python detector** (`detector/`): a standalone script (`detect_wheelchair.py`) run directly against a virtual environment whose dependencies are pinned in `requirements.txt`. No packaging or wheel building is configured.
- **Toolchain version pinning**: `mise.toml` at the repo root pins Python to `3.12` via the [mise](https://mise.jdx.dev/) tool manager.

## Key files and packages

- `mise.toml` — repo-wide tool version declaration (`python = "3.12"`).
- `whoosh_ramah/pubspec.yaml` — Flutter package manifest: declares `flutter`, `firebase_core`, `cloud_firestore`, `material_ui`, `cupertino_icons`, `intl`; sets `publish_to: 'none'` and `version: 1.0.0+1`.
- `whoosh_ramah/android/app/build.gradle.kts` — Android Gradle build; contains a `release { ... }` block that is currently commented out with a TODO noting signing keys are not configured yet.
- `whoosh_ramah/android/build.gradle.kts`, `settings.gradle.kts` — top-level Android/Gradle project config generated by Flutter.
- `detector/requirements.txt` — Python deps: `opencv-python>=4.8`, `python-dotenv>=1.0`, `firebase-admin>=6.4`, `inference-sdk>=0.20`, `ultralytics>=8.2`.
- `detector/.env.example` / `detector/.env` — runtime configuration for the detector (Firebase credentials, model path).
- `whoosh_ramah/firebase.json` — Firebase CLI configuration for the Flutter app.
- `whoosh_ramah/analysis_options.yaml` — Dart lint rules (via `flutter_lints`).

## Architecture and conventions

- **Multi-language, per-subproject builds.** Each language keeps its own dependency file (`pubspec.yaml`, `requirements.txt`) and relies on its SDK's standard tooling. There is no cross-cutting build script.
- **No published artifacts.** The Flutter app is explicitly marked `publish_to: 'none'` in `pubspec.yaml`, indicating it is not intended for distribution via pub.dev.
- **Versioning:** Flutter app uses semantic versioning format `1.0.0+1` (build-name + build-number) as documented in the `pubspec.yaml` comments, which map to Android `versionName`/`versionCode` and iOS `CFBundleShortVersionString`/`CFBundleVersion`.
- **Android release builds are stubbed.** `android/app/build.gradle.kts` defines a `release {}` block but leaves signing configuration as a `// TODO`, with a comment stating debug keys are used temporarily so `flutter run --release` works.
- **Fonts are bundled locally.** `pubspec.yaml` embeds Nunito font variants under `assets/fonts/` so the demo does not require internet access.
- **Python env isolation.** The detector ships a `venv/` directory alongside the code, implying developers activate the local venv rather than relying on system Python.

## Conventions and constraints

- Tool versions are managed through mise: `mise.toml` declares `python = "3.12"` (enforced by mise when activated).
- Flutter dependencies are resolved via `flutter pub get` from `pubspec.yaml`; the lockfile `pubspec.lock` pins exact transitive versions.
- Python dependencies use minimum-version constraints (`>=`) in `requirements.txt` rather than exact pins.
- Android release signing is intentionally left unconfigured — the `release` block in `android/app/build.gradle.kts` is a TODO placeholder; production APK signing is not set up.
- No CI, Docker, Makefile, or release automation exists in this repository. Builds are expected to be run manually by contributors using their local Flutter/Python environments.
