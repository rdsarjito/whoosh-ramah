## Overview

The repository contains two independent codebases sharing a Firestore schema:

- **Flutter app** (`whoosh_ramah/`) — passenger and attendant screens built on Material UI.
- **Python detector** (`detector/`) — webcam/video wheelchair detection script that posts tasks to Firestore.

There is no shared error-handling framework, no custom exception hierarchy, and no centralized logging. Each side uses idiomatic language-level patterns.

## Flutter (Dart) Error Handling

### Patterns observed

1. **`try / catch` around async service calls.**
   - `PenumpangPesanScreen._kirim()` wraps `_svc.buatPermintaan(...)` in `try { ... } catch (_) { ... }`, then shows a `SnackBar` with the message `'Gagal mengirim permintaan. Silakan coba lagi.'` and resets loading state.
   - `PetugasDetailScreen._majukan()` wraps `_service.majukanStatus(...)` similarly, showing `'Gagal memperbarui status. Silakan silakan coba lagi.'` via `ScaffoldMessenger.of(context).showSnackBar(...)`.
   - Both handlers guard against post-dispose calls with an explicit `if (!mounted) return;` before touching `context`.

2. **StreamBuilder snapshot errors are rendered inline.**
   - Screens using `StreamBuilder<Permintaan?>` check `snapshot.hasError` alongside `connectionState == ConnectionState.waiting` to distinguish loading from error states.
   - Example messages: `'Gagal memuat tugas. Periksa koneksi Anda.'` (when stream errored) vs `'Tugas tidak ditemukan.'` (when data is null).

3. **Platform configuration failures use `UnsupportedError`.**
   - `lib/firebase_options.dart` (generated by FlutterFire CLI) throws `UnsupportedError` for every unsupported platform branch (web, iOS, macOS, Windows, Linux, default), instructing the user to re-run the FlutterFire CLI.

4. **No custom error types or sentinel errors exist.**
   - There is no `errors/` directory, no domain-specific exception classes, and no `Result<T, E>`-style wrapper. Errors bubble as Dart exceptions and are swallowed at the screen layer.

5. **Theme integrates an error color.**
   - `theme.dart` defines `AppColors.redPrimary` and assigns it to the `error` slot of the theme's color scheme, giving error-related UI a consistent red hue.

6. **Tests assert absence of unexpected exceptions.**
   - `test/text_scale_test.dart` uses `tester.takeException()` and asserts it is `isNull`, treating unhandled widget build exceptions as test failures.

### Conventions

- User-facing errors are surfaced through `ScaffoldMessenger.showSnackBar` with short Indonesian messages.
- Network/stream failures are not rethrown; they are converted into a user-visible "retry" prompt.
- Async operations set a local `_loading` boolean so the UI can show a spinner and disable buttons during the operation.

## Python Detector Error Handling

### Patterns observed

1. **Configuration and setup failures raise `SystemExit`.**
   - Missing Roboflow API key → `raise SystemExit("ROBOFLOW_API_KEY belum diisi di .env...")`
   - Missing local model file → `raise SystemExit(f"File model '{MODEL_LOKAL}' tidak ditemukan...")`
   - Missing Firebase credentials file → `raise SystemExit(f"File kunci Firebase '{FIREBASE_KEY}' tidak ditemukan...")`
   - Camera source cannot be opened → `raise SystemExit(f"Tidak bisa membuka sumber video: {args.sumber}")`

2. **Runtime detection errors are caught and logged via `print`.**
   - The per-frame call to `model.deteksi(frame)` is wrapped in `try: ... except Exception as e:` with the comment `# koneksi putus, dsb.` (connection drops, etc.). On failure it prints `[peringatan] Deteksi gagal: {e}` and continues with an empty detection list rather than aborting the loop.

3. **No structured logging library is used.**
   - All diagnostics go through `print()` with bracketed tags like `[info]`, `[model]`, `[firebase]`, `[deteksi]`, `[peringatan]`.

4. **No custom exception classes exist.**
   - Only `SystemExit` (for fatal configuration/runtime issues) and bare `Exception` (caught generically) are used.

## Cross-cutting Observations

- There is **no shared error contract** between the Flutter app and the Python detector. They communicate only through Firestore documents; error propagation across the boundary happens implicitly via document state (e.g., a task remains in `menunggu` if the detector fails to write).
- Neither side implements retry logic, circuit breakers, or error metrics collection.
- Error messages are written in Indonesian throughout both codebases, matching the product's target audience.
- The design mockups under `design/` do not define error/error-state screens explicitly beyond comments such as `/// Kerangka loading / error: hero + pesan di tengah` in `keluarga_pantau_screen.dart` and `penumpang_status_screen.dart`, indicating a convention of centering a hero + message for loading/error states.
